redmine-cli ships two complementary integrations, both vendor-neutral:

- **Agent Skill** -- a `SKILL.md` instruction set following the open [Agent Skills standard](https://agentskills.io), supported by 35+ agents (Claude, Codex, Gemini, Cursor, Copilot, Cline, Goose, Windsurf, Roo, Junie, ...). Teaches the agent how to drive the CLI effectively.
- **MCP Server** -- `redmine mcp serve` exposes the CLI over the [Model Context Protocol](https://modelcontextprotocol.io). Best for hosts that discover tools through MCP.

For most hosts you want both. Several major hosts (Claude Code, Codex CLI, Gemini CLI) support a one-step plugin install that bundles them together.

## Quick install

<InstallTabs />

- **Any agent** uses the [skills.sh](https://skills.sh) installer (`npx skills add`), which detects your agent and writes `SKILL.md` to the right location (`.claude/skills/`, `.codex/skills/`, `.gemini/skills/`, or the cross-vendor `.agents/skills/` fallback). The bundled wrapper is `redmine install-skill [--global]`.
- **Claude Code / Codex CLI / Gemini CLI** bundle the skill and MCP server in a single plugin install. After installing, run `/reload-plugins` (Claude) or restart the CLI to activate.
- **MCP host** is the manual route for Cursor, VS Code, Zed, Claude Desktop, and other MCP-aware hosts. Add `redmine mcp serve` (with optional `--profile`, `--enable-writes`, `--enable-groups`, ...) to your host's MCP config; see your host's MCP setup docs for the exact file path and JSON shape.
- **Docker** runs the MCP server from the `ghcr.io/aarondpn/redmine-mcp` image without installing `redmine` at all. See [Run with Docker](#run-with-docker).

<Aside type="note">
  Prerequisite for the non-Docker paths: `redmine` must be on the host's `PATH` and you must have logged in once via `redmine auth login`. The skill-only path additionally needs Node.js for `npx skills add`.
</Aside>

## Agent Skill

The skill teaches the agent what `--help` cannot: output formats, pagination, filtering, name resolution, and common workflows. After installing it the agent knows to extract fields with `--jq`, check exit codes instead of parsing errors from stdout, inspect attachments, and fall back to `--help` instead of guessing flags.

The full skill source: [`skills/redmine-cli/SKILL.md`](https://github.com/aarondpn/redmine-cli/blob/main/skills/redmine-cli/SKILL.md). Copy directly into your agent's instructions if you prefer not to run an installer.

## MCP Server

`redmine mcp serve` exposes the CLI as a [Model Context Protocol](https://modelcontextprotocol.io) server over stdio by default, or over streamable HTTP when `--http` is passed. MCP-aware hosts can then drive Redmine through tool calls, reusing the same profile-backed authentication as every other `redmine` command.

### How it works

- **Transport:** stdio by default. The host can spawn `redmine mcp serve` and talk JSON-RPC over its standard streams, or you can pass `--http :8080` to expose the same server over streamable HTTP.
- **Authentication:** the active profile is used by default. Override with `--profile <name>`, `--server` / `--api-key`, or the `REDMINE_*` environment variables -- exactly like every other subcommand.
- **Read-only by default.** Mutating tools (create / update / delete, comment, close, reopen, and similar write operations) are registered only when `--enable-writes` is passed. Without the flag they never appear in `tools/list`. For a second, transport-level guarantee, set [read-only mode](/getting-started/configuration/#read-only-mode) (`read_only: true` in the profile or `REDMINE_READ_ONLY=1`) -- it blocks every write at the HTTP layer, even when `--enable-writes` is passed.
- **Verified status changes.** `update_issue` (with `status_id`), `close_issue` and `reopen_issue` read the issue back and return a tool error when Redmine silently ignored the transition, naming the allowed statuses on Redmine 5.0+ (`close_issue` / `reopen_issue` accept an issue that is already in another closed / open status). Other changes in the same call (such as notes) may already have been applied. The CLI behaves the same way, see [status changes are verified](/commands/issues/#status-changes-are-verified).
- **Verified wiki parent changes.** `create_wiki_page` and `update_wiki_page` accept `parent_title`, and `list_wiki_pages` reports each page's `parent`. Redmine silently ignores a parent change on an existing page without the `rename_wiki_pages` permission, so these tools read the page back and return a tool error when the parent did not change. `update_wiki_page` resends the current text when `text` is omitted, so `{project_id, page, parent_title}` is enough to move a page. The CLI behaves the same way, see [parent changes are verified](/commands/wiki/#parent-changes-are-verified).
- **ID lookups.** `list_priorities` and `list_time_entry_activities` (with `project_id` for the activities of one project, including project-specific overrides whose IDs differ from the global ones) return the numeric IDs the write tools expect for `priority_id` and `activity_id`.
- **Editing comments.** `update_journal` (a write tool, Redmine 5.0+) changes the `notes` or `private_notes` of a comment by journal ID; get the IDs from `get_issue` with `includes: ["journals"]`. An empty `notes` string removes the comment from the history. Redmine answers success even when it ignores a change (for example `private_notes` without the "Set notes as private" permission), so re-read the issue to confirm.
- **Categories and attachments.** `create_issue_category`, `update_issue_category` (`assigned_to_id: 0` clears the default assignee), `delete_issue_category`, `update_attachment` and `delete_attachment` are write tools; `get_issue_category` is read-only. `delete_issue_category` accepts `reassign_to_id` to move the issues to another category, which must belong to the same project: Redmine silently ignores a foreign target and would leave the issues uncategorized, so the tool rejects it instead. There is no MCP tool for attachment thumbnails (binary data); use `redmine attachments thumbnail` from the CLI.
- **News.** `list_news` and `get_news` are read-only (the `news` group); `create_news`, `update_news` and `delete_news` are write tools. Redmine answers a news create without a body, so `create_news` looks the new item up afterwards (newest item in the project with the same title, summary and description by the current user) and returns its `id`; when it cannot be determined the `id` is omitted and a warning is added, so re-read with `list_news` instead of retrying the create. News comments cannot be written through the API; `get_news` with `includes: ["comments"]` only reads them.
- **Custom field values.** Write tools for issues, projects, time entries, versions, users, my account and groups accept `custom_field_values`, keyed by numeric custom field ID (`list_custom_fields`; names are rejected). Each value is a string, or an array of strings for a multi-value field; `""` clears a field. A one-element array is sent as a plain string, so it is also valid for single-value fields. `create_time_entry` needs it on servers with required time entry custom fields.
- **API keys stay out of MCP.** No tool or resource returns a Redmine API key. `get_my_account`, `me`, `get_user`, `list_users`, `create_user`, and `redmine://user/...` strip `api_key` from the user record before it reaches the client, even if Redmine includes it in the response, and their output schemas do not declare the field. The CLI is unaffected: `redmine my-account get` still shows your own key.
- **Configurable surface.** `--enable-groups` / `--disable-groups` constrain the registered tools to specific categories (`issues`, `wiki`, `time`, `news`, ...). For sharper control, `--enable-tools` / `--disable-tools` allow- or deny-list individual tool names. Run `redmine mcp tools` to print the full catalog. Resources follow the same filters as the matching read tool, so a host can't use a resource to read data its tools are denied:

  | Resource | Registered when this tool is enabled |
  | --- | --- |
  | `redmine://issue/{id}` | `get_issue` |
  | `redmine://project/{identifier}` | `get_project` |
  | `redmine://user/{id}` | `get_user` (numeric IDs) or `me` (`redmine://user/me`) |
  | `redmine://time-entry/{id}` | `get_time_entry` |
  | `redmine://wiki/{project}/{page}` | `get_wiki_page` |
  | `redmine://version/{id}` | `get_version` |

  With no `--enable-tools` / `--disable-tools` filter, every resource in the enabled groups stays available. A resource whose tool is filtered out answers with the standard "Resource not found" error (JSON-RPC code `-32602`); for `redmine://user/{id}` that also applies to the half whose tool is disabled, for example `redmine://user/me` when only `get_user` is enabled.

<Aside type="caution">
  Write tools are destructive. Prefer leaving them disabled unless the host surfaces a per-call approval UI you trust.
</Aside>

### Run with Docker

The `ghcr.io/aarondpn/redmine-mcp` image (linux/amd64 and linux/arm64) runs `redmine mcp serve` directly. You don't need a local install, a profile, or a keyring. Pass the server URL and API key as environment variables instead. Every `REDMINE_*` variable and every `redmine mcp serve` flag works the same way inside the container. Flags go after the image name.

| Tag | Tracks |
|---|---|
| `latest` | Newest stable release |
| `2`, `2.13`, `2.13.0` | Major, minor, or exact release |

#### Local: stdio

The MCP host starts a fresh container per session and talks to it over stdin/stdout. `-i` is required; `--rm` cleans up afterwards. The `-e NAME` form (without `=value`) forwards the variable from the host's environment, so the key never lands in the args list.

**Claude Code:**

```bash
claude mcp add redmine \
  -e REDMINE_SERVER=https://redmine.example.com \
  -e REDMINE_API_KEY=your-api-key \
  -- docker run -i --rm -e REDMINE_SERVER -e REDMINE_API_KEY ghcr.io/aarondpn/redmine-mcp
```

**Claude Desktop, Cursor, Windsurf, and other hosts using the `mcpServers` JSON shape:**

```json
{
  "mcpServers": {
    "redmine": {
      "command": "docker",
      "args": ["run", "-i", "--rm", "-e", "REDMINE_SERVER", "-e", "REDMINE_API_KEY", "ghcr.io/aarondpn/redmine-mcp"],
      "env": {
        "REDMINE_SERVER": "https://redmine.example.com",
        "REDMINE_API_KEY": "your-api-key"
      }
    }
  }
}
```

VS Code prompts for the URL and API key and stores the key as a secret. Cursor installs placeholder values: open the server in Cursor's MCP settings and replace `REDMINE_SERVER` and `REDMINE_API_KEY` afterwards.

To enable writes or narrow the tool surface, add flags after the image name (`... ghcr.io/aarondpn/redmine-mcp --enable-writes --enable-groups issues,time`) or forward the matching `REDMINE_MCP_*` variable.

Already have a `~/.redmine-cli.yaml` with profiles? Mount it read-only and pick a profile. `--user` keeps the file readable even though `redmine auth login` writes it with mode `0600`. Profiles that store their secret in the system keyring can't be read inside the container; supply `REDMINE_API_KEY` for those.

```bash
docker run -i --rm --user "$(id -u):$(id -g)" \
  -v "$HOME/.redmine-cli.yaml:/config.yaml:ro" \
  ghcr.io/aarondpn/redmine-mcp --config /config.yaml --profile work
```

#### Shared: HTTP server with Docker Compose

To run one server for a whole team, use the HTTP transport. The repository ships a ready-made [`compose.yaml`](https://github.com/aarondpn/redmine-cli/blob/main/docker/compose.yaml) and [`.env.example`](https://github.com/aarondpn/redmine-cli/blob/main/docker/.env.example):

```bash
curl -fsSLO https://raw.githubusercontent.com/aarondpn/redmine-cli/main/docker/compose.yaml
curl -fsSL https://raw.githubusercontent.com/aarondpn/redmine-cli/main/docker/.env.example -o .env
# set REDMINE_SERVER, REDMINE_API_KEY and REDMINE_MCP_AUTH_TOKEN (openssl rand -hex 32) in .env
docker compose up -d
```

Then point clients at the server with the token:

```bash
claude mcp add --transport http redmine http://localhost:8080/ \
  --header "Authorization: Bearer $REDMINE_MCP_AUTH_TOKEN"
```

The compose file only publishes the port on `127.0.0.1`. Set `REDMINE_MCP_PUBLISH=0.0.0.0:8080` in `.env` to reach it from other machines, and put a TLS-terminating reverse proxy in front so the bearer token isn't sent in clear text.

Without Compose, the same server is a single command. `REDMINE_MCP_HTTP` replaces the `--http` flag:

```bash
docker run -d --name redmine-mcp -p 127.0.0.1:8080:8080 \
  -e REDMINE_SERVER -e REDMINE_API_KEY -e REDMINE_MCP_AUTH_TOKEN \
  -e REDMINE_MCP_HTTP=0.0.0.0:8080 \
  ghcr.io/aarondpn/redmine-mcp
```

If you leave out `REDMINE_MCP_AUTH_TOKEN`, the server generates a token at startup and prints it to the container log (`docker logs redmine-mcp`). That token changes on every restart, so set your own for anything long-lived.

<Aside type="caution">
  The HTTP server authenticates to Redmine with a single API key, so every client acts as that Redmine user. Use a dedicated account whose project permissions match what the agents should be able to do.
</Aside>

### HTTP transport

Pass `--http <addr>` to expose the server over streamable HTTP instead of stdio. The address shorthand `:8080` (no host) is rewritten to `127.0.0.1:8080` so the server is never accidentally reachable from other machines. Pass an explicit host to listen elsewhere:

```bash
# Loopback only
redmine mcp serve --http :8080

# Explicit loopback (equivalent)
redmine mcp serve --http 127.0.0.1:8080

# Listen on every interface -- always pair with a token.
# umask 077 creates the token file readable only by you from the start.
(umask 077; openssl rand -hex 32 > ~/.redmine-mcp-token)
redmine mcp serve --http 0.0.0.0:8080 --auth-token-file ~/.redmine-mcp-token
```

The umask only applies when the file is created. If the token file already exists, run `chmod 600 ~/.redmine-mcp-token` before writing a new token into it.

When a non-loopback bind is detected without a token, the server generates a random token for that run and prints it to stderr. Pass `--no-auth` (or `REDMINE_MCP_NO_AUTH=1`) only if something in front of the server, such as an authenticating reverse proxy, already checks clients; the CLI then prints a warning and serves without a token.

A loopback bind without a token keeps working, but anyone with access to the machine can reach it: every local user and process can call the tools as your Redmine user. The server prints a warning at startup; set a token to close it. An explicit `--no-auth` on a loopback bind serves without a token and without a warning. Whatever the bind, requests that reach a loopback listener with a non-loopback `Host` header are rejected with `403`, which blocks DNS-rebinding attacks from web pages open in a local browser.

The server applies `ReadHeaderTimeout=10s`, `ReadTimeout=30s`, and `IdleTimeout=120s`; `WriteTimeout` is left unbounded so slow Redmine instances don't terminate in-flight tool calls.

The HTTP transport is stateless, so it speaks MCP revision `2026-07-28` (sessionless, `server/discover` instead of the `initialize` handshake). Every tool call is a self-contained Redmine API request, so there is no session to keep. Practical consequences: only `POST` is served (`GET` and `DELETE` answer `405`), and stream resumption via `Last-Event-ID` is not available. Older clients negotiate down to `2025-11-25` and keep working unchanged.

Clients must send the bearer token on every request:

```http
POST / HTTP/1.1
Authorization: Bearer <token>
Content-Type: application/json
```

Pass the token with `--auth-token-file <path>`, or `--auth-token-file -` to read it from standard input (`pass show redmine-mcp | redmine mcp serve --http :8080 --auth-token-file -`). Surrounding whitespace such as a trailing newline is ignored. The token can also live in the config block (`mcp.auth_token`) or `REDMINE_MCP_AUTH_TOKEN`, and the listen address in `mcp.http` or `REDMINE_MCP_HTTP`. Flags override both. For profiles with `credential_store: keyring`, `mcp.auth_token` is moved into the system keyring on the next save, like the API key (see [System keyring](/getting-started/configuration/#system-keyring-optional)). If `redmine mcp serve --http` then can't read the keyring (for example a locked keychain over SSH, or `REDMINE_NO_KEYRING=1`), it refuses to start rather than serve without the token; supply the token another way, or pass `--no-auth` to serve without authentication on purpose.

`--auth-token <token>` also works, but the token then shows up in `ps` output and shell history. Prefer `--auth-token-file`, `REDMINE_MCP_AUTH_TOKEN`, or `mcp.auth_token`.

<Aside type="danger">
  The bearer token is the only thing standing between any HTTP-reachable client and your Redmine instance through this server. Generate it with a CSPRNG, never reuse it across deployments, and prefer terminating TLS in front of the server (reverse proxy) when binding outside loopback.
</Aside>

### Narrowing the exposed tools

For an issue-only assistant, drop everything but the issues group:

```bash
redmine mcp serve --enable-groups issues
```

To enable writes everywhere except destructive deletes, combine the flags:

```bash
redmine mcp serve --enable-writes --disable-tools delete_issue,delete_project,delete_wiki_page
```

The same defaults can live in `~/.redmine-cli.yaml` per profile, and CLI flags override them:

```yaml
profiles:
  internal:
    server: https://redmine.internal
    api_key: ...
    mcp:
      enable_writes: true
      enable_groups: [issues, wiki]
      disable_tools: [delete_issue]
```

Environment variables (`REDMINE_MCP_ENABLE_GROUPS`, `REDMINE_MCP_DISABLE_GROUPS`, `REDMINE_MCP_ENABLE_TOOLS`, `REDMINE_MCP_DISABLE_TOOLS`, `REDMINE_MCP_ENABLE_WRITES`, `REDMINE_MCP_AUTH_TOKEN`, `REDMINE_MCP_HTTP`, `REDMINE_MCP_NO_AUTH`) override the config block.

### Prerequisite

`redmine` must be on the host's `PATH` and a profile must already be logged in (`redmine auth login`). No Node.js required. With [Docker](#run-with-docker), you only need Docker and an API key.

### Troubleshooting

<Steps>

1. **Host reports "command not found".** The spawned process inherits the host's `PATH`, which often differs from your shell. Use an absolute path (`which redmine`) in the `command` field.

2. **Tools list is empty or missing mutations.** `--enable-writes` was not passed, the surface was narrowed via `--enable-groups` / `--enable-tools`, or the host cached an older `tools/list`. Run `redmine mcp tools` to see the full catalog and restart the host after changing args.

3. **Only a `setup_status` tool, or the server instructions say Redmine is not connected.** No server or credentials are configured (or the profile's keyring secret cannot be read), so `redmine mcp serve` stays up instead of exiting, without Redmine tools, and tells the agent what to do. Run `redmine auth login` in a terminal (or `redmine auth login --server https://redmine.example.com --api-key-file -` with the key on stdin), or set `REDMINE_SERVER` and `REDMINE_API_KEY` in the host's MCP `env` block, then restart or reconnect the MCP server. Never paste the key into the chat; no tool accepts one. The same message goes to stderr, which hosts show in the server log. This only applies to stdio: with `--http` the command exits with the error instead. An unknown `--profile <name>` or invalid `--enable-groups` / `--enable-tools` values still fail at startup.

4. **Warning on stderr about rejected credentials (401 / 403).** At startup the server checks the credentials in the background (without delaying the connection) and warns, naming the profile and server, when Redmine rejects them. Run `redmine auth login` to update them, or fix `REDMINE_API_KEY` in the host config, then restart the MCP server. Network errors during that check are not reported; tools report them when called.

5. **401 / "no profile" errors.** No profile is logged in, or `--profile <name>` points at one that does not exist. Run `redmine auth list` to confirm.

</Steps>
