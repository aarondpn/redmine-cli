The `attachments` command (aliases `attachment`, `a`) surfaces Redmine's [Attachments API](https://www.redmine.org/projects/redmine/wiki/Rest_api#Attachments) so you can inspect an attachment's metadata and download its bytes. Downloads reuse the active profile's server and API key, streaming straight to disk - no `curl`, no manually extracted key.

<Aside type="tip">
  Don't know the attachment ID? List an issue's attachments with
  [`redmine issues get <id> --attachments`](/commands/issues/#get) - it prints each
  attachment's ID, filename, size, and content type.
</Aside>

## get

```bash
redmine attachments get <id> [flags]
```

Aliases: `show`, `view`, `metadata`. Fetches the attachment's ID, filename, size, content type, description, author, and creation time via `GET /attachments/:id.json`. Table output also shows the download URL (when present); `json` returns every field, including `content_url`.

| Flag | Description |
|------|-------------|
| `-o, --output` | Output format: `table`, `json`, `csv` |

## download

```bash
redmine attachments download <id> [flags]
```

Aliases: `dl`, `get-file`. Streams the attachment's raw bytes to disk (or stdout), authenticating with the active profile. The response is streamed, never buffered entirely in memory, so large files are safe.

| Flag | Description |
|------|-------------|
| `-d, --dir`    | Directory to save into, using the attachment's real filename (created if missing) |
| `--path`       | Exact destination file path. Use `-` to stream to stdout |
| `--clobber`    | Overwrite an existing file at the destination |
| `-o, --output` | Confirmation format: `json` prints a result object; otherwise a human line is written to stderr |

With no destination flag, the file is saved as `./<filename>` in the current directory.

### Existing files and `--clobber`

Downloads never overwrite an existing file unless you pass `--clobber`. This applies to `--path`, `--dir`, and the default current directory. Without it, the command fails before downloading and names the path:

```text
failed to download attachment 42: logo.png already exists; use --clobber to overwrite it
```

The bytes are first streamed into a temporary file in the destination directory and moved into place only once the download has completed. As a result:

- A failed or interrupted download leaves any existing file untouched and leaves no partial file at the destination. Pressing Ctrl-C once stops the download and removes its temporary file. If the process is killed outright (a second Ctrl-C, `kill -9`), a hidden `.redmine-download-*.tmp` file may remain in the destination directory; it is safe to delete.
- A symlink at the destination is never followed. Without `--clobber` it counts as an existing file (even when it is dangling); with `--clobber` the link itself is replaced by the downloaded file, and whatever it pointed to is left alone.
- A directory (or other non-regular file such as a FIFO or device) at the destination is always an error, even with `--clobber`.
- A new file gets the same permissions as any other file you create (`0644` with the usual umask `022`). With `--clobber`, a replaced regular file keeps its previous permissions.

Without `--clobber`, the final step uses a hard link, which fails atomically if a file appeared at the destination while the download was running. On filesystems without hard-link support the CLI falls back to re-checking the destination and then renaming, which leaves a small window between the check and the rename.

<Aside type="caution" title="Changed behavior">
  Earlier versions silently truncated an existing file at the destination and
  wrote through symlinks. Scripts that re-download into the same location now
  need `--clobber`.
</Aside>

With `--dir` or the default destination the filename comes from the server. It is reduced to its base name, so it can never escape the directory. A name that starts with `.` (such as `.bashrc` or `.gitconfig`) is still saved, but a warning is printed to stderr because it may shadow a configuration file. `--path -` (stdout) is unaffected by any of this.

If the server redirects the download (or any other request), the redirect is followed only when it stays on the configured server (the same host and port, or the `https://` upgrade of an `http://` server, port 80 becoming 443), or goes to a public address (for example presigned object-storage URLs such as S3). Credentials are only sent to the configured server, never to the redirect target. Redirects from `https://` to `http://`, or to loopback, private, link-local, multicast, unspecified (`0.0.0.0/8`), carrier-grade NAT (`100.64.0.0/10`), or benchmarking (`198.18.0.0/15`) addresses are refused, including IPv6 addresses that embed one of them (IPv4-mapped, NAT64 `64:ff9b::/96`, 6to4 `2002::/16`); host names are re-checked against the address actually connected to. Another port on the configured server's host gets the same checks as any other host. A redirect to a public `http://` URL is followed as long as it does not come from an `https://` URL.

<Aside>
  Unlike most commands, `-o/--output` here controls only the **confirmation**
  output, not where the bytes go - use `--dir` / `--path` for that. When
  streaming to stdout (`--path -`), the bytes go to stdout and the confirmation
  always goes to stderr, so the pipe stays clean even with `-o json`.
</Aside>
