## list

```bash
redmine issues list [flags]
```

| Flag | Description |
|------|-------------|
| `--project`              | Filter by project (name, identifier, or ID) |
| `--tracker`              | Filter by tracker (name or ID) |
| `--status`               | Filter by status: `open`, `closed`, `*`, name, or ID |
| `--assignee`             | Filter by assignee: `me`, `none` (unassigned), user or group name, login, or ID. See [assignee resolution](#assignee-resolution) |
| `--author`               | Filter by author: `me`, name, login, or ID. An unresolvable name is an error, see [assignee resolution](#assignee-resolution) |
| `--priority`             | Filter by priority (name or ID) |
| `--category`             | Filter by issue category (name or ID) |
| `--version`              | Filter by target version (name or ID) |
| `--parent`               | Restrict to children of a parent issue ID |
| `--subproject`           | Subproject filter: numeric ID, or `!*` to exclude subprojects |
| `--include-subprojects`  | Include issues from subprojects (default `true`; pair with `=false` to exclude) |
| `--is-private`           | Filter by privacy: `true` returns private issues only, `false` public only |
| `--filter`               | Raw Redmine filter as `key=value` (repeatable). Use for date ranges, custom fields, subject text |
| `--query`                | Run a saved query by name (see [`queries`](/commands/queries/)) |
| `--query-id`             | Run a saved query by numeric ID (mutually exclusive with `--query`) |
| `--sort`                 | Sort order, e.g. `updated_on:desc` |
| `--include`              | Include related data: `attachments`, `relations` (repeatable or comma-separated; unknown values are rejected) |
| `--attachments`          | Shorthand for `--include attachments` |
| `--relations`            | Shorthand for `--include relations` |
| `--limit`                | Maximum number of results (0 for all) |
| `--offset`               | Result offset for pagination |
| `-o, --output`           | Output format: `table`, `json` |

<Aside type="tip">
  `--filter` is an escape hatch for Redmine's filter operator syntax. Examples:

  - `--filter created_on='>=2025-01-01'` — created on or after a date
  - `--filter updated_on='><2025-01-01|2025-12-31'` — updated in a range
  - `--filter cf_5='Critical'` — custom field `cf_5` equals "Critical"
  - `--filter subject='~login'` — subject contains "login"
</Aside>

## get

```bash
redmine issues get <id> [flags]
```

Aliases: `show`, `view`.

| Flag | Description |
|------|-------------|
| `--include`                | Include related data: `journals`, `children`, `relations`, `attachments`, `watchers`, `changesets`, `allowed_statuses` (Redmine 5.0+), `reactions` (Redmine 7.1+); repeatable or comma-separated, unknown values are rejected |
| `--journals`               | Shorthand for `--include journals` |
| `--children`               | Shorthand for `--include children` |
| `--relations`              | Shorthand for `--include relations` |
| `--watchers`               | Shorthand for `--include watchers` |
| `--attachments`            | List the issue's attachments (id, filename, size, content type) |
| `--download-attachments`   | Download every attachment of the issue into the given directory |
| `--clobber`                | With `--download-attachments`, overwrite files that already exist in the directory |
| `--allow-hidden`           | With `--download-attachments`, allow saving attachments whose filename starts with `.` |
| `-o, --output`             | Output format |

`--download-attachments` never overwrites a file that already exists in the directory unless you pass `--clobber`, and refuses server-supplied names starting with `.` (such as `.bashrc` or `.envrc`) unless you pass `--allow-hidden`. Every destination is checked before anything is downloaded, so a conflict aborts the command without writing any file. The same rules as [`attachments download`](/commands/attachments/#existing-files-and---clobber) apply: symlinks are never followed, directories are never replaced, and a failed download leaves no partial file.

Attachments of the same issue often share a filename (for example several `screenshot.png`). They are all kept: the newest (the one with the highest attachment ID, usually a corrected re-upload) keeps its name and older ones get their attachment ID added, such as `screenshot (attachment-71).png`. Names that differ only in case are treated as the same name on every platform, because macOS and Windows filesystems usually cannot hold both. Each confirmation on stderr shows the path the attachment was saved to. This renaming only covers names within one download; `--clobber` covers files that were already there.

    redmine issues get 123 --download-attachments ./issue-123

    redmine issues get 123 --download-attachments ./issue-123 --clobber
    ```
  </TabItem>
  <TabItem label="Read fully">

    redmine issues get 123 --journals --children --relations --watchers --download-attachments ./issue-123
    redmine issues get 123 --include journals,attachments,children,relations,watchers -o json

    # Statuses the current user may move the issue to
    redmine issues get 123 --include allowed_statuses -o json
    ```
  </TabItem>
</Tabs>

With `-o json` (and in the MCP `get_issue` tool) the issue carries these optional keys. They are omitted, not `null`, when Redmine does not send them:

- `status.is_closed` (Redmine 5.0+), `closed_on`, `total_estimated_hours` (on lists only from Redmine 5.0).
- `spent_hours` and `total_spent_hours`, only when you have the `view_time_entries` permission; on lists only from Redmine 5.0.
- `children`, a recursive tree of `id`, `tracker`, `subject` and nested `children`.
- `changesets` with `--include changesets`, and `allowed_statuses` with `--include allowed_statuses` (Redmine 5.0+).
- Journal `updated_on` (Redmine 6.0+, present on every journal) and `updated_by` (set when the notes were edited).
- `reactions` on the issue and on journals with `--include reactions` (Redmine 7.1+).

The table view shows every field Redmine sent and leaves out the ones that are empty or absent (for example because the Redmine version or your permissions do not provide them): category, private flag, closed date, estimated and spent hours (with the subtree totals in parentheses), custom fields, watchers and allowed statuses as detail rows, followed by the children tree, relations (worded from this issue's side, for example `blocked by #7`) and changesets when requested with the matching include. Journals with only property changes are shown too, one line per change (`* Status: 1 -> In Progress`). Status, priority, tracker, project, category, version, user and custom field IDs are shown as names when the issue itself carries them (the example shows `Status: 1 -> In Progress` because the old status is not part of the response; with `--include allowed_statuses` both would be names), otherwise as the raw ID.

```text
ID:               #123
Project:          Demo
Tracker:          Bug
Status:           In Progress
Priority:         High
Subject:          Crash on login
Author:           Alice
Assignee:         Bob
Category:         Backend
Done Ratio:       30%
Created:          2026-01-01T09:00:00Z
Updated:          2026-01-02T10:00:00Z
Estimated Hours:  4.00 (total 6.00)
Spent Hours:      1.50
Custom Fields:    Env: prod
Watchers:         Bob, Carol

Children:
  #124 [Bug] Fix session
    #125 Add test

Relations:
  blocks #130

--- Alice (2026-01-01T10:00:00Z) [journal 41] ---
* Status: 1 -> In Progress
* Assignee: (none) -> Bob

Taking this one.
```

In the table view each comment header carries its journal ID, for example `--- Alice (2026-01-01T10:00:00Z) [journal 41] ---`, with `(edited 2026-01-03T09:00:00Z by Carol)` (or just `(edited)` when Redmine omits the time) after the date when the notes were changed later, and `(private)` for private notes. That ID is what [`issues comment edit`](#edit-a-comment) takes.

<Aside type="tip">
  `--attachments` surfaces each attachment's ID. Feed that ID to
  [`attachments download <id>`](/commands/attachments/#download) to fetch a single
  file, or use `--download-attachments <dir>` to grab them all at once.
</Aside>

## create

```bash
redmine issues create [flags]
```

| Flag | Description |
|------|-------------|
| `--project`         | Project (name, identifier, or ID) — falls back to the default project of the active profile |
| `--subject`         | Issue subject — <Badge text="required" variant="danger" /> |
| `--tracker`         | Tracker (name or ID) |
| `--status`          | Status (name or ID) |
| `--priority`        | Priority (name or ID) |
| `--assignee`        | Assignee: `me`, user or group name, login, or ID. `none` clears the assignee on `update`; on `create` it sets no assignee, though Redmine may still apply the category or project default assignee. See [assignee resolution](#assignee-resolution) |
| `--description`     | Issue description |
| `--description-file` | Read the description from a file (`-` reads standard input); mutually exclusive with `--description`; an empty or whitespace-only file is rejected |
| `--parent`          | Parent issue ID |
| `--category`        | Category (name or ID) |
| `--version`         | Target version (name or ID) |
| `--start-date`      | Start date (`YYYY-MM-DD`) |
| `--due-date`        | Due date (`YYYY-MM-DD`) |
| `--estimated-hours` | Estimated hours |
| `--done-ratio`      | Completion percentage (0-100). Redmine ignores it when % done is derived from the status or from subtasks |
| `--private`         | Mark as private |
| `--watcher`         | Initial watcher (name, login, ID, or `me`; repeatable) |
| `--custom-field`    | Custom field value as `name=value` or `id=value` (repeatable; repeat a field for multi-value fields, `name=` clears it). See [custom field values](#custom-field-values) |
| `--attach`          | File path to attach (repeatable) |
| `--attach-description` | Description of the file given by the `--attach` at the same position (repeatable; pass `""` to skip a file). See [attachment descriptions](#attachment-descriptions) |

```bash
redmine issues create --project myproject --subject "Add search" --tracker Feature --priority High

redmine issues create --project myproject --subject "Bug report" \
  --start-date 2026-05-01 --due-date 2026-05-15 \
  --watcher me --watcher "QA Bot" \
  --custom-field Severity=High \
  --attach /path/to/screenshot.png --attach /path/to/log.txt

# Values with spaces: quote the whole pair and repeat the flag per field
redmine issues create --project myproject --subject "Bug" \
  --custom-field "2=Value for field 2" \
  --custom-field "61=Value for 61"

# Multi-value field: repeat the flag with the same field
redmine issues create --project myproject --subject "Cross-platform bug" \
  --custom-field Platforms=Linux --custom-field Platforms=macOS

# Child issue under an epic, with a category
redmine issues create --project myproject --parent 1234 --tracker Task \
  --category "Backend" --subject "Implement API endpoint"

# Attach a screenshot and embed it inline in a Textile description (!filename!);
# on servers using Markdown/CommonMark formatting write ![](screenshot.png) instead
redmine issues create --project myproject --subject "Broken layout" \
  --attach ./screenshot.png --description 'Layout breaks on resize: !screenshot.png!'

# Long Textile/Markdown description from a file, no shell quoting needed
redmine issues create --project myproject --subject "Spec" --description-file spec.textile

# Describe attachments: the Nth --attach-description belongs to the Nth --attach
redmine issues create --project myproject --subject "Crash" \
  --attach ./crash.log --attach-description "Server log" \
  --attach ./trace.txt --attach-description "Stack trace"
```

If Redmine starts the new issue in a different status than `--status` asked for (its workflow does not allow new issues of that tracker to start there for your role), the command prints a warning on stderr. It still exits `0`, because the issue was created and a retry would duplicate it.

### Attachment descriptions

`--attach-description` pairs with `--attach` by position: the first description belongs to the first file, the second to the second, and so on. You may give fewer descriptions than files; the remaining files get none, and an empty description (`--attach-description ""`) skips a file. More descriptions than files is an error, raised before anything is uploaded. The same pair of flags exists on `issues update`, `wiki create/update` and `news create/update`.

### Custom field values

`--custom-field` takes `key=value` pairs, where the key is a custom field name or its numeric ID.

- Names resolve against `GET /custom_fields.json`, which is admin-only, and only among the custom fields of the resource's type. An issue command never picks a time entry field of the same name.
- Non-admins must use numeric IDs. Find them in the `custom_fields` array of the JSON output, for example `redmine issues get 123 --jq '.custom_fields'`.
- The value is everything after the first `=`, verbatim. Spaces and further `=` characters are kept. Quote the whole pair and repeat the flag per field.
- For a multi-value field, repeat the flag with the same field: `--custom-field Platforms=Linux --custom-field Platforms=macOS`. The order is kept.
- A single-value field given several values fails. The CLI checks this when the field was given by name; when it was given by ID, Redmine answers `validation_failed` ("is invalid") and the error hint points at the repeated field.
- `--custom-field Name=` clears the field, including every value of a multi-value field. An empty value cannot be combined with other values for the same field.
- The same flag exists on `projects create/update`, `time log/update`, `versions create/update`, `users create/update`, `my-account update` and `groups create/update`.

<Aside type="tip" title="Validation errors">
  Projects and trackers can make fields such as category, version, or custom
  fields required. When Redmine rejects a create or update with
  `validation_failed`, the error carries a hint (and a `hint` field in JSON
  mode) pointing at the commands that list valid values, for example
  `redmine projects get myproject --include trackers,issue_categories,issue_custom_fields`,
  `redmine versions list --project myproject --open`, and
  `redmine memberships list --project myproject` (assignable users). Redmine's
  own messages are localized, so rely on the error `code`, not the message text.
</Aside>

## update

```bash
redmine issues update <id> [flags]
```

Accepts the same flags as `create` (except `--watcher`) plus:

| Flag | Description |
|------|-------------|
| `--project`        | Move the issue to this project (name, identifier, or ID). See [project moves are verified](#project-moves-are-verified) |
| `--remove-attachment` | Attachment ID to remove from the issue (repeatable). Asks for confirmation unless `--force` is given |
| `--force`, `-f`    | Skip the `--remove-attachment` confirmation |
| `--note`           | Add a journal note |
| `--note-file`      | Read the journal note from a file (`-` reads standard input); mutually exclusive with `--note`; an empty or whitespace-only file is rejected |
| `--description-file` | Read the new description from a file (`-` reads standard input); mutually exclusive with `--description`; an empty or whitespace-only file is rejected (pass `--description ""` to clear the description) |
| `--private-notes`  | Mark the journal note from `--note` / `--note-file` as private |
| `--done-ratio`     | Completion percentage (0-100) |
| `--start-date`     | Start date (empty string clears) |
| `--due-date`       | Due date (empty string clears) |
| `--custom-field`   | Custom field value as `name=value` or `id=value` (repeatable; repeat a field for multi-value fields, `name=` clears it). See [custom field values](#custom-field-values) |
| `--attach`         | File path to attach (repeatable) |
| `--attach-description` | Description of the file given by the `--attach` at the same position (repeatable; pass `""` to skip a file). See [attachment descriptions](#attachment-descriptions) |

```bash
redmine issues update 123 --note "Fixed the bug" --attach /path/to/fixed_code.patch

# Private journal note visible only to staff
redmine issues update 123 --note "Internal context" --private-notes

# Update custom field by name
redmine issues update 123 --custom-field Severity=Critical

# Clear a custom field
redmine issues update 123 --custom-field Severity=

# Assign to a group by name, or clear the assignee
redmine issues update 123 --assignee "Backend Team"
redmine issues update 123 --assignee none

# Long description from a file, note piped in on stdin
redmine issues update 123 --description-file description.textile
generate-report | redmine issues update 123 --note-file -

# Move the issue to another project
redmine issues update 123 --project other-project

# Remove two attachments (IDs from `issues get 123 --attachments`) without asking
redmine issues update 123 --remove-attachment 45 --remove-attachment 46 --force
```

When you move an issue with `--project`, `--category`, `--version` and `--assignee` names are resolved in the target project. Redmine keeps the category if the target project has one with the same name, keeps the version only if it is shared with the target project, and switches the tracker to the target project's first tracker if the current one is not enabled there.

`--remove-attachment` deletes the attachments for good. Redmine ignores IDs of attachments that belong to another issue, and silently ignores `--remove-attachment` without permission to edit the issue (`edit_issues`) while still answering with success; check the result with `redmine issues get <id> --attachments`. The confirmation prompt reads standard input, so combining `--remove-attachment` with `--description-file -` or `--note-file -` requires `--force`.

### Project moves are verified

Redmine silently keeps the issue in its project when you may not add issues in the target project (Add issues permission, issue tracking enabled, at least one tracker). So after a move the CLI reads the issue back. If it was not moved, the command fails with exit status `1` and code `project_not_applied`; like [`status_not_applied`](#status-changes-are-verified), the details warn when other changes in the same request may already have been applied.

### Status changes are verified

Redmine answers an issue update with success even when it **silently ignores** the requested status: transitions its workflow does not allow for your role and the issue's tracker are dropped, and so is closing an issue that still has open subtasks or is blocked by an open issue. So whenever a status change is requested (`update --status`, `close`, `reopen`), the CLI reads the issue back. If the status did not change, the command fails like any other error, with exit status `1`:

- the message explains what happened and names the current status,
- the details list the statuses you *can* move the issue to (Redmine 5.0+; older servers cannot report them) and, when the request carried more than the status, warn that those other changes (fields, notes, attachments) may already have been applied, so do not resend them blindly,
- with `-o json`, this is the standard [error envelope](/guides/output-formats/#json-error-envelope) with code `status_not_applied`.

`close` and `reopen` only care about open versus closed: closing an issue that is already in another closed status (say `Rejected`) succeeds with a note on stderr instead of failing. Updates without a status change do not trigger the extra request.

In JSON mode `stdout` stays empty and the envelope is a single line, the last line of `stderr`:

```bash
$ redmine issues close 123 -o json 2>err.log
$ echo $?
1
$ tail -n1 err.log
{"error":{"message":"Issue #123: status was not changed to \"Closed\" (ID 5); it is now \"New\" (ID 1). Redmine silently ignores status transitions that its workflow does not allow for your role and the issue's tracker, and refuses to close issues that have open subtasks or are blocked by open issues.","code":"status_not_applied","details":["Allowed statuses: New (1), In Progress (2), Resolved (3), Feedback (4)."]}}
```

On success the action envelope is unchanged; to see the issue after an update, run `redmine issues get <id>`.

## assign

```bash
redmine issues assign <id> <assignee> [flags]
```

The assignee argument accepts a numeric ID, `me`, a user or group name, a login, or `none` to clear the assignee.

```bash
redmine issues assign 123 me
redmine issues assign 123 "Backend Team"   # a group that is a project member
redmine issues assign 123 none             # unassign
```

### Assignee resolution

`--assignee` (and the `assign` / `watchers` user argument) resolves names like this:

1. Numeric IDs, `me`, and `none` are used directly, with no name lookup.
2. With project context, names are matched (case-insensitively) against the
   project's members, users and groups alike. The context is `--project` (or the
   default project) for `list` and `create`, and the issue's own project for
   `update`, `assign`, and `watchers`. Project memberships are readable by any
   project member, so this works without admin rights.
3. The users list, which Redmine only exposes to administrators, is checked
   when the input could be a login (no spaces), when several members share the
   name, or when no member matched. An exact login match wins over display
   names, so `--assignee max` picks the user whose login is `max` even if
   another member is displayed as "Max". Without admin rights the membership
   match stands.

When nothing matches, the error lists the project's members (marked `[user]`
or `[group]`) so you can pick the right name or ID. When two members share a
name and no login settles it, the CLI asks for the numeric ID instead of
picking one.

<Aside type="caution" title="Unresolvable list filters fail">
  `issues list` / `browse` stop with an error when an `--assignee` or
  `--author` name cannot be resolved, with or without `--project`. Earlier
  versions printed a warning and listed issues without the filter. Without
  admin rights, pass `--project` so names can be matched against its members,
  or use a numeric ID or `me`.
</Aside>

<Aside type="note">
  Assigning an issue to a group requires the Redmine setting **Allow issue
  assignment to groups** (Administration → Settings → Issue tracking), and the
  group must have an assignable role in the project.
</Aside>

## comment

```bash
redmine issues comment <id> --message "Your comment" [flags]
```

| Flag | Description |
|------|-------------|
| `-m, --message`      | Comment text |
| `-F, --message-file` | Read the comment from a file (`-` reads standard input); mutually exclusive with `--message`; an empty or whitespace-only file is rejected |

```bash
redmine issues comment 123 --message-file notes.textile
git log -1 --format=%B | redmine issues comment 123 -F -
```

File contents are sent as read (UTF-8, no trimming; only a leading byte-order mark is dropped), so multi-line Textile or Markdown needs no shell quoting.

### Edit a comment

<Badge text="Redmine 5.0+" variant="note" />

```bash
redmine issues comment edit <journal-id> [flags]
```

Comments are identified by their **journal ID**, not the issue ID. Redmine has no endpoint to fetch a single journal, so list them from the issue:

```bash
redmine issues get 123 --journals --jq '.journals[] | {id, notes}'
```

| Flag | Description |
|------|-------------|
| `-m, --message`      | New comment text. An empty string is rejected; use `--clear` to remove the text |
| `-F, --message-file` | Read the new text from a file (`-` reads standard input); mutually exclusive with `--message`; an empty or whitespace-only file is rejected |
| `--private`          | Make the comment private |
| `--public`           | Make the comment public; mutually exclusive with `--private` |
| `--clear`            | Remove the comment's text; mutually exclusive with `--message` and `--message-file` |
| `-f, --force`        | Skip the confirmation that `--clear` asks for |

At least one of these flags is required. The command prints an `updated` action for resource `journal`.

```bash
redmine issues comment edit 456 --message "Corrected: deployed to production"
redmine issues comment edit 456 --message-file notes.textile
redmine issues comment edit 456 --private
redmine issues comment edit 456 --clear --force
```

<Aside type="note">
  Editing the text needs the "Edit issue notes" permission (or "Edit own issue notes" for your own comments). `--private` and `--public` need "Set notes as private"; Redmine silently ignores them without it. Redmine answers success even when it did not apply a change, so check the result with `issues get --journals`. Servers older than 5.0 do not accept this request over the API; the command then fails with an error whose hint points at the version requirement.
</Aside>

`--clear` removes the comment from the issue history: Redmine 5.x and 7.0 delete a journal that records no other change, and 6.x keeps an empty row that the API no longer lists. Because it cannot be undone, the command asks for confirmation unless you pass `--force`; declining prints a cancelled `updated` action and changes nothing.

## copy

```bash
redmine issues copy <id> [flags]
```

Creates a copy of an issue, in the same or another project. Redmine copies the fields, custom fields and parent; the copy starts in the tracker's default status, you are its author, and the watchers are copied when you may add watchers in the target project. Requires the Copy issues permission.

| Flag | Description |
|------|-------------|
| `--project`          | Project for the copy (name, identifier, or ID); defaults to the source issue's project |
| `--subject`          | Subject of the copy (defaults to the source subject) |
| `--tracker`          | Tracker (name or ID) |
| `--status`           | Status (name or ID); defaults to the tracker's default status |
| `--priority`         | Priority (name or ID) |
| `--assignee`         | Assignee: `me`, user or group name, login, or ID, resolved in the target project; `none` leaves the copy unassigned |
| `--link`             | Relate the copy to the original (`copied_to` / `copied_from`) |
| `--with-attachments` | Copy the attachments |
| `--with-subtasks`    | Copy the subtasks |
| `--output`, `-o`     | Output format: `table`, `json` |

```bash
# Copy an issue within its project
redmine issues copy 123

# Copy into another project, linked to the original, with attachments and subtasks
redmine issues copy 123 --project other-project --link --with-attachments --with-subtasks

# Copy with a new subject and assignee
redmine issues copy 123 --subject "Same bug on staging" --assignee me
```

Redmine settings can override the flags: *Link issues on copy* (Administration > Settings > Issue tracking) can force or forbid `--link`, and on Redmine 6.0+ *Copy attachments on copy* does the same for `--with-attachments`. A copy into another project is only linked when *Allow cross-project issue relations* is enabled.

## watchers

```bash
redmine issues watchers list <id>
redmine issues watchers add <id> <user>...
redmine issues watchers remove <id> <user>
```

`<user>` accepts a numeric ID, login, full name, or `me`. Names are matched against the issue's project members first (see [assignee resolution](#assignee-resolution)). `watchers add` takes several users and adds them in one request; Redmine skips users that cannot watch the issue.

```bash
redmine issues watchers add 123 me
redmine issues watchers add 123 alice bob 42
redmine issues watchers list 123
redmine issues watchers remove 123 alice
```

## relations

```bash
redmine issues relations list <id>
redmine issues relations get <relation-id>
redmine issues relations add <id> --to <other-id> --type <type> [--delay <days>]
redmine issues relations remove <relation-id>
```

| Flag | Description |
|------|-------------|
| `--to`    | Target issue ID — <Badge text="required" variant="danger" /> |
| `--type`  | Relation type. Default `relates`. See table below |
| `--delay` | Number of days delay. Only valid for `precedes`/`follows` |

Supported relation types (from the [Redmine REST docs](https://www.redmine.org/projects/redmine/wiki/Rest_IssueRelations)):

| Type | Meaning |
|------|---------|
| `relates`     | Generic association |
| `duplicates`  | This issue duplicates the target |
| `duplicated`  | This issue is duplicated by the target |
| `blocks`      | This issue blocks the target |
| `blocked`     | This issue is blocked by the target |
| `precedes`    | This issue precedes the target (accepts `--delay`) |
| `follows`     | This issue follows the target (accepts `--delay`) |
| `copied_to`   | This issue was copied to the target |
| `copied_from` | This issue was copied from the target |

```bash
redmine issues relations add 123 --to 124 --type blocks
redmine issues relations add 123 --to 124 --type precedes --delay 5
redmine issues relations list 123
redmine issues relations get 42
redmine issues relations remove 42
```

<Aside type="note">
  `relations get` and `relations remove` take the **relation ID**, not an issue ID. Use `relations list` first to discover the relation IDs on an issue. `relations get` prints the relation as JSON with `-o json`, or as a detail view (ID, issue, related issue, type, delay) otherwise.
</Aside>

## open

```bash
redmine issues open <id>
```

Constructs the issue URL from your configured Redmine server and opens it in your default browser.

```bash
redmine issues open 123   # → https://redmine.example.com/issues/123
```

The URL must be an absolute `http` or `https` URL; anything else is refused. The browser is launched with `open` (macOS), `xdg-open` (Linux and BSD) or `rundll32 url.dll,FileProtocolHandler` (Windows), never through a shell.

## browse

```bash
redmine issues browse [flags]
```

Opens an interactive terminal browser for issues. Accepts the same filter flags as [`list`](#list).
